# 先规格，后搬砖

## 为什么这样省

一次"生成 → 编译 → 报错 → 改 → 再编译"的循环，token 消耗通常是首次生成的 3~8 倍。
设计决策只发生一次，但需要判断力。

结论：**把智力花在不产生循环的地方，把循环交给便宜的模型。**

## 三段流程

### 第 1 段｜强模型只出规格书，不写代码

开场必须把约束说死，否则它一定会开始写代码然后进编译循环：

> 不要写任何 SCL 或 LAD 代码，只输出规格书，格式按模板。
> 有歧义的地方列进「待确认」，不要自己假设。

这一段通常一两个来回就结束。

### 第 2 段｜弱模型分块搬砖

每个块单独一个任务，输入三样东西：

1. 规格书里**这一个块**的那一节
2. 一个现有块做参照 —— 先 `d_read_block` 取出来贴进去
3. 硬约束：「只写这一个块，不要碰别的块」

执行链：

```
d_read_block(参照块) → d_write_block(不带 confirm，只出计划) → 人工审计划 → 带 confirm 落库 → d_compile
```

### 第 3 段｜强模型只做审查

把最终代码 + 规格书一起给它，只问一句：

> 对照规格书，列出不符合的地方和缺失的联锁。不要重写，只列问题。

审查的 token 消耗远低于生成，而且这一步最容易抓到逻辑错 —— 编译器抓不到的那部分。

## 规格书模板

```markdown
# 规格书：<功能名>

## 1. 范围
- 目标：
- 涉及设备：
- 明确不做：（防模型自作主张加功能）

## 2. 块清单
| 块名 | 类型 | 语言 | 调用方 | 说明 |
|---|---|---|---|---|

## 3. 接口
### <块名>
| 方向 | 名称 | 数据类型 | 初值 | 注释 |
|---|---|---|---|---|
| Input | | | | |

## 4. 变量表
| 符号名 | 地址 | 数据类型 | 注释 |
|---|---|---|---|

## 5. 联锁与安全
| 条件 | 信号 | 极性 | 作用位置 | 后果 |
|---|---|---|---|---|
| 急停 | | 常闭 | | 切断所有输出 |

## 6. 步序（有状态机才填）
| 步 | 进入条件 | 动作 | 转移条件 | 下一步 |
|---|---|---|---|---|

## 7. 验收标准
- [ ] 编译 0 错
- [ ] <行为断言，例如：停止按钮断线时电机必须停>

## 8. 待确认
-
```

## 铁律

1. **一次只写一个块** —— "写整个工程"既是额度杀手，也是质量杀手
2. **dry-run 不落库** —— 审计划比审代码便宜，比调试便宜一万倍
3. **编译门免费用** —— 编译不过就重试，不花钱；过了才允许保存
4. **参照现有块** —— 比凭空写准得多，还顺带继承了工程原有的命名规范
5. **规格书写清"不做什么"** —— 模型最爱自作主张加它认为你需要的功能
